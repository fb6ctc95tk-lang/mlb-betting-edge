# DCR-W4-007 — WP-4 Orchestrator Stage Transaction Boundaries

**Design Change Record**
**Work Package:** WP-4: Run Orchestrator Core
**Oracle Phase:** Oracle Phase 1
**Project:** MLB Betting Edge / Edge Oracle
**Status:** Adopted — PM authorized 2026-07-26
**Supersedes:** (gap) — P1-WP4-T06 and P1-WP4-T07 in `ORACLE_PHASE_1_IMPLEMENTATION_BACKLOG.md` contained no transaction boundary specification for Stages 2–10

---

## 1. Identified Gap

The Oracle Phase 1 Implementation Plan (WP-4 section) and Implementation Backlog (P1-WP4-T05 through T07) describe the operational sequence for each Orchestrator stage but contain no explicit statement about transaction granularity for Stages 2–10.

DCR-W5-001 explicitly governs Stage 1 atomicity (§10) and establishes that the WP-4 Orchestrator is the transaction owner (§6, §8). It does not address when, or how many times, the Orchestrator should commit across Stages 2–10.

The WP-4 implementation proceeded with one independent transaction per stage — an interpretation of DCR-W5-001 §6 — but this interpretation was not approved before implementation. This constitutes a governance sequencing defect, which this DCR resolves retroactively.

---

## 2. Process Deviation Record

**Nature of deviation:** Engineering interpretation executed before governance approval.

The original WP-4 T05–T08 authorization (issued 2026-07-25) included the following stop condition:

> "Stop immediately if: [...] transaction ownership is ambiguous"

Stage 1 transaction ownership is not ambiguous — DCR-W5-001 §10 explicitly governs it. Stage 2–10 transaction granularity is absent from all approved documents.

Implementation proceeded with one-transaction-per-stage for Stages 2–10 without escalating this gap before writing code.

**Technical assessment:** No known technical defect. The selected model is internally consistent, aligned with the only explicit precedent (Stage 1), and consistent with the caller-owned transaction principle established by DCR-W5-001.

**Governance assessment:** The stop condition required escalation before implementation. Implementation proceeded instead. This DCR resolves the governance gap. It does not constitute acceptance of the deviation as appropriate process. Future ambiguities of this kind must be escalated before implementation begins.

## 4. Adopted Decision

### Stage 1

Stage 1 remains governed by DCR-W5-001 §10. It executes as one atomic caller-owned transaction. The Orchestrator commits after all required Stage 1 operations succeed: advisory lock acquisition, Slate Run ID generation, `oracle_slate_runs` INSERT, `slate_initialized` event INSERT, and `run_status` UPDATE to `schedule_loaded`.

No change to Stage 1 behavior.

### Stages 2–10

Each stage executes as an independent caller-owned transaction. The following rules apply to every stage from Stage 2 through Stage 10:

1. **Kill switch check:** The kill switch is checked before any database work begins for that stage. A halt at this point does not commit or roll back; no transaction has been opened for the new stage.
2. **Single shared connection and transaction:** All database operations for that stage — record INSERTs, Event Store calls, and state machine UPDATE writes — execute on the same connection within one transaction.
3. **Commit after complete stage success:** The Orchestrator commits only after all database operations assigned to that stage succeed. A partial stage does not commit.
4. **No child service commits:** No WP-3 or WP-5 function commits, rolls back, or closes the connection. These functions create and close cursors only.
5. **Stage failure:** If any operation within a stage raises an exception before the stage-level commit, the Orchestrator does not commit. The caller is responsible for calling `conn.rollback()` to discard any partial writes from that stage.
6. **Durability of earlier stages:** A failure in Stage N does not roll back Stages 1 through N−1. Their transactions were committed independently and remain durable.
7. **No cross-stage transactions:** No transaction spans more than one stage. The stage is the unit of commit.

### Recovery Semantics

Per-stage commits create durable checkpoints at each stage boundary. After a failure, the database reflects all stages that committed successfully before the failure point.

Restart semantics, replay logic, duplicate-run detection beyond the Stage 1 advisory lock, and idempotency enforcement are explicitly deferred. They must not be implemented until authorized by a separate PM authorization.

---

## 5. Rationale

**One transaction per stage** is the minimal extension of the DCR-W5-001 §10 precedent. DCR-W5-001 §10 depicts Stage 1 as one atomic unit; applying the same structure per stage avoids cross-stage transaction coupling with no document authority to justify it.

**Failure isolation:** A failure in Stage 5 must not roll back Stage 3's committed game status updates. Independent stage transactions enforce this. A shared cross-stage transaction would silently undo prior-stage work on any later-stage failure.

**Advisory lock scope:** The Stage 1 advisory lock is transaction-scoped. If Stage 1 and later stages shared a transaction, the lock would be held for the entire run duration, blocking concurrent runs on the same date. Per-stage commits release it at Stage 1 commit, as DCR-W5-001 §10 explicitly intends.

**Debuggability:** Committed stage records are inspectable in the database before subsequent stages run. A partial run (e.g., kill switch deactivated mid-run) leaves a queryable audit trail.

---

## 6. Rejected Alternatives

**One transaction for all Stages 2–10:** Rejected. A failure in any late stage would roll back all game records, event records, and state changes from all prior stages, making failure forensics harder and inconsistent with the durable checkpoint model.

**One transaction for all 10 stages (including Stage 1):** Rejected. The advisory lock must be released at Stage 1 commit per DCR-W5-001 §10. A single spanning transaction would hold the lock through Stage 10, blocking the duplicate-run guard for the entire run duration.

The existing `backend/oracle/orchestrator.py` (P1-WP4-T05–T07, untracked, not yet committed) implements one independent transaction per stage for Stages 2–10. This matches the decision adopted in §4 of this DCR.

**No implementation change is required.**

## 9. Final Governance Decision

**Stage 1 transaction:** Governed by DCR-W5-001 §10. Unchanged.

**Stages 2–10 transaction granularity:** One independent caller-owned transaction per stage. Commit after all database operations for that stage succeed. No cross-stage transaction.

**Process deviation:** Recorded in §2. No technical defect. Governance escalation was required before implementation and did not occur. This DCR resolves the gap retroactively with PM authorization dated 2026-07-26.
