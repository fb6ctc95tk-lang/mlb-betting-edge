# DCR-W5-001 — Event Store Connection and Transaction Ownership

**Design Change Record**
**Work Package:** WP-5: Event Store Service
**Oracle Phase:** Oracle Phase 1
**Project:** MLB Betting Edge / Edge Oracle
**Status:** Adopted — PM authorized 2026-07-25
**Supersedes:** WP-5 service contract signature published in `ORACLE_PHASE_1_IMPLEMENTATION_PLAN.md` Section 2 and `ORACLE_PHASE_1_IMPLEMENTATION_BACKLOG.md` P1-WP5-T02

---

## 1. Identified Conflict

The Oracle Phase 1 Implementation Plan (Section 2, WP-5 Service Contract) and the Oracle Phase 1 Implementation Backlog (P1-WP5-T02 Description) both publish the following `record_event()` signature:

```
record_event(event_type, slate_run_id, event_timestamp, game_run_id=None, play_id=None, payload=None) -> event_id
```

This signature contains no database connection parameter. It is silent on who obtains the connection, who owns the transaction, and who is responsible for commit and rollback. This omission creates a contradiction with two established requirements:

1. **WP-3 connection contract (DCR-W4-005).** The Identifier Lifecycle Manager (`generate_slate_run_id`, `generate_play_id`) requires a caller-supplied psycopg2 connection with autocommit disabled. The caller owns the transaction lifecycle. No WP-3 function opens a connection, commits, or rolls back.

2. **WP-4 Stage 1 atomicity requirement.** Stage 1 of the Run Orchestrator must execute three database operations as a single atomic unit: (a) acquire the advisory lock and determine the next Slate Run ID sequence value, (b) INSERT into `oracle_slate_runs`, and (c) INSERT the `slate_initialized` event into `oracle_play_events`. If the Event Store opens an independent connection with its own transaction boundary, operations (b) and (c) would reside in separate transactions. A failure between them would leave `oracle_slate_runs` with a committed record but no corresponding event, violating the event-first integrity principle of the Oracle immutable event model.

## 3. Options Assessed

**Option A — Caller-owned connection and transaction**

`record_event()` accepts a caller-supplied psycopg2 connection as its first positional parameter. The caller (the WP-4 Orchestrator) opens the connection, opens the transaction, calls WP-3 functions and WP-5 in sequence within that transaction, and commits or rolls back. The Event Store creates and closes cursors only.

- Advantage: All Stage 1 operations execute in a single transaction. Stage 1 atomicity is preserved. Aligns with DCR-W4-005 and the WP-3 model.
- Risk: WP-5 service contract must be updated; callers must supply a connection.

**Option B — Event Store manages its own connection**

`record_event()` opens a new connection internally for each call, performs its INSERT, and closes the connection.

- Advantage: Matches the originally published signature exactly (no conn parameter).
- Risk: Stage 1 operates across two independent transactions. An application failure between the `oracle_slate_runs` INSERT and the event INSERT leaves an orphaned slate run record with no `slate_initialized` event — a state the Oracle event model does not permit. This cannot be corrected at the application layer without violating append-only semantics.

**Option C — Optional connection parameter**

`record_event()` accepts an optional `conn` parameter. When `conn` is None, the function opens its own connection. When `conn` is supplied, it uses the caller's.

- Advantage: Maintains backward compatibility with the published signature in the no-conn case.
- Risk: Two code paths within the same function. The autonomous-connection path retains the atomicity problem from Option B. Callers may incorrectly use the no-conn path for operations that require atomicity.

---

## 4. Adopted Option

**Option A — Caller-owned connection and transaction**

---

## 5. Rationale

The Stage 1 atomicity requirement is not negotiable. The Oracle event model requires that every state change be durably recorded in `oracle_play_events` before the application treats it as committed. An `oracle_slate_runs` record without a corresponding `slate_initialized` event is an inconsistent state that the architecture explicitly prohibits. Option B creates this inconsistency whenever a failure occurs between the slate run INSERT and the event INSERT.

Option A eliminates this risk entirely by executing all Stage 1 operations in the caller's transaction. The Orchestrator commits once, after all three operations succeed. If any operation fails, the entire transaction rolls back, and no partial state is persisted.

Option A is also the natural extension of the design pattern established by WP-3 (DCR-W4-005). The Orchestrator already owns the connection and transaction when calling WP-3 functions. Adding WP-5 to the same ownership model requires no architectural change — only a signature update to formalize what the atomicity requirement already implied.

Option C was rejected because it introduces a code-path bifurcation that invites misuse and provides no advantage that Option A does not also provide.

---

## 6. Transaction Ownership

The caller (WP-4 Orchestrator) owns the transaction.

The Event Store participates in the caller's existing transaction. It does not create a new transaction, savepoint, or subtransaction. All INSERT operations performed by `record_event()` are committed or rolled back as part of the caller's transaction.

---

## 7. Connection Ownership

The caller (WP-4 Orchestrator) owns the database connection.

The Event Store receives the connection as a function parameter. It creates and closes psycopg2 cursors against that connection. It does not close the connection, acquire it from a pool, or store it as module state.

The connection must have autocommit disabled at the time `record_event()` is called. The Event Store enforces this requirement identically to the WP-3 Identifier Manager.

---

## 8. Commit and Rollback Ownership

The caller owns commit and rollback.

`record_event()` does not call `conn.commit()` or `conn.rollback()`. These operations belong to the Orchestrator. This is identical to the WP-3 constraint documented in the Identifier Manager's DATABASE CONNECTION CONTRACT docstring.

---

## 9. WP-3 Compatibility

Option A is fully compatible with the WP-3 Identifier Manager. Both use the same caller-owned connection model. The Orchestrator already holds a connection with autocommit disabled when calling `generate_slate_run_id()` in Stage 1. Passing the same connection to `record_event()` requires no change to the WP-3 implementation.

---

## 10. WP-4 Stage 1 Atomicity

Stage 1 of the Run Orchestrator (P1-WP4-T05) executes the following operations within a single transaction:

1. `pg_advisory_xact_lock()` — acquire advisory lock for the Slate Run ID sequence (WP-3)
2. `SELECT COUNT(*)` on `oracle_slate_runs` — determine next sequence value (WP-3)
3. `INSERT` into `oracle_slate_runs` — create the slate run record (Orchestrator)
4. `INSERT` into `oracle_play_events` — write `slate_initialized` event (WP-5)
5. `COMMIT` — Orchestrator commits; advisory lock released; both records become visible atomically

Under Option A, steps 1–4 share the caller's connection and transaction. Step 5 is the Orchestrator's commit. If any of steps 1–4 raises an exception, the Orchestrator's exception handler calls `conn.rollback()`, and no records are persisted.

Under the original published signature (Option B), step 4 would occur in a separate transaction. A failure between steps 3 and 4 would leave `oracle_slate_runs` committed with no event.

## 11. WP-5 Implementation Consequences

The approved `record_event()` signature is:

```python
record_event(
    conn: object,
    event_type: str,
    slate_run_id: str,
    event_timestamp: datetime,
    game_run_id: str | None = None,
    play_id: str | None = None,
    payload: dict | None = None,
) -> int
```

`conn` is the first positional parameter. It receives the caller's psycopg2 connection. The function must:

- Verify that `conn.autocommit` is `False` (or that autocommit is disabled) before executing any cursor operation; raise `InvalidConnectionStateError` if not — consistent with the WP-3 guard implemented in `identifier_manager._require_manual_transaction()`
- Validate `event_type` against the 28-event-type registry; raise `ValueError` before any cursor operation if unknown
- Validate `slate_run_id` using `is_valid_slate_run_id()`; raise `ValueError` before any cursor operation if invalid
- Execute one INSERT into `oracle_play_events` using a cursor opened against `conn`
- Close the cursor in a `finally` block
- Return the `event_id` assigned by BIGSERIAL (retrieved via `RETURNING event_id`)
- Contain no `conn.commit()`, `conn.rollback()`, or `conn.close()` calls
- Contain no UPDATE or DELETE SQL

No other WP-5 module-level state, connection pool, or deferred connection is permitted.

## 12. Testing Consequences

**Unit tests (P1-WP5-T03):**

Unit tests call `record_event()` with a lightweight mock connection object — the same pattern used in WP-3 unit tests (`_MockCursor` / mock connection pattern in `test_oracle_identifier_manager.py`). Tests for `ValueError` on unknown event type and invalid `slate_run_id` verify that the error is raised before any cursor operation reaches the database. No live database connection is required for these tests.

**Integration tests (P1-WP5-T04):**

Integration tests supply a real psycopg2 connection with autocommit disabled. The test owns the transaction: it calls `record_event()`, queries `oracle_play_events`, asserts the result, and then calls `TRUNCATE oracle_play_events` for teardown (because DELETE is blocked by the append-only trigger). This is the established teardown pattern from `test_oracle_schema.py` and `test_oracle_append_only.py`.

**WP-4 T08 Orchestrator tests:**

When WP-4 T05–T08 are implemented, the integration test for Stage 1 will open one connection with autocommit disabled, invoke the Orchestrator, and verify that both the `oracle_slate_runs` record and the `slate_initialized` event appear in the database after a single commit. No separate connection for the Event Store is opened during the test.

## 14. Rejected Alternatives

**Option B (Event Store manages own connection):** Rejected. Breaks Stage 1 atomicity. Creates orphaned `oracle_slate_runs` records on failure between slate run INSERT and event INSERT. Incompatible with the Oracle event model's requirement that all state changes be recorded durably before being treated as committed.

**Option C (Optional connection parameter):** Rejected. Introduces two code paths with different transaction semantics. The autonomous-connection path retains the atomicity problem. The risk of callers incorrectly using the no-connection path for atomic operations is not acceptable.

---

## 15. Final Governance Decision

**Connection ownership:** Caller. The WP-4 Orchestrator supplies a psycopg2 connection to `record_event()`.

**Transaction ownership:** Caller. The Orchestrator opens the transaction, calls WP-3 and WP-5 functions within it, and commits or rolls back.

**Commit ownership:** Caller. `record_event()` does not commit.

**Rollback ownership:** Caller. `record_event()` does not roll back.

**Approved signature:** `record_event(conn, event_type, slate_run_id, event_timestamp, game_run_id=None, play_id=None, payload=None) -> event_id`

**Planning documents to correct:** `ORACLE_PHASE_1_IMPLEMENTATION_PLAN.md` Section 2 WP-5 and `ORACLE_PHASE_1_IMPLEMENTATION_BACKLOG.md` P1-WP5-T02 and P1-WP5-T03.

**Architecture documents:** No modification required or authorized.

**Implementation authorization:** WP-5 implementation remains unauthorized. This DCR resolves Governance Condition 1 from the WP-5 Readiness Assessment (2026-07-25). A separate PM authorization is required to begin WP-5 implementation.

## Non-Blocking Deferred Matters (Recorded for Completeness)

**R-3 policy (trigger does not write to `oracle_immutability_audit`):** The WP-2 trigger implementation deviates from the trigger specification in the Plan (Section 2 WP-2) and the Architecture (Section 13.1, 13.3). This deviation is reflected in the committed migration 006 and the accepted WP-2 test suite. A formal ADR or DCR documenting this decision is still outstanding. This does not block WP-5 implementation but must be resolved before WP-6 (Phase 1 Integration Verification) is authorized, because the current WP-6 EC-3 test specification asserts audit rows that R-3 policy prevents from being written.

**Event-type count label (27 vs. 28):** The architecture, plan, and backlog label the event type list as "27 types" but the enumeration contains 28 items. The Architecture Lock Section 9 designates this as non-blocking and deferred, confirming that the enumeration is authoritative. WP-5 must implement the 28-item list as enumerated. No document change is authorized by this DCR.
